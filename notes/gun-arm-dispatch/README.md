# Hero art read off the switch that selects it

21 shared-bank names, derived from control flow rather than from a render:
13 weapon-state arms on `[0x0A]`, and 8 waterline sprites on `[0x05]`.

## Why these resisted everything else

`notes/shared-bank-geometry/` named 52 offsets from cross-stage consensus:
the same picture is called walk-left frame 14 by CAPSULE, CAVES and PRISON
independently, and unanimity across two or more stages settles it.

Two groups had no such consensus to form. The forked arms around `0x33F2` and
`0x35B4` have one named drawer between them; the single-pixel dots at
`0x5BF8..0x5C1C` have none, and rendering a one-pixel dot at an unknown
palette tells you it is a dot.

They did not need a render. The code says what they are.

## The dispatch

Both directions of the armed hero are a switch on `[0x0A]`, one arm polygon
per case:

```
jne [0x0A], 0x02, <next case>
video type=0, offset=CV_33F2, ...      <- the arm for case 2
jg  [0x06], [0x30], <ret>              <- only while charge <= threshold
mov [0xF8], [0x31]
and [0xF8], 0x0004                     <- and a timer bit is set
je  [0xF8], 0x00, <ret>
video type=0, offset=CV_5C0C, ...      <- the dot, only while blinking
```

A case number is not an index anyone assigned to the art — it is the value the
VM compares against. Reading it is not "naming from the index": NAMING.md §2
bars the *disassembler's* encounter order, which carries no meaning. This
carries the machine's.

    $ python3 notes/gun-arm-dispatch/arm_case_table.py
    switch starting at CV_347C (6 files)     switch starting at CV_35B4 (6 files)
      case 1: CV_347C  + CV_5BF8               case 1: CV_35B4
      case 2: CV_33F2  + CV_5C0C               case 2: CV_35D0
      case 3: CV_3420  + CV_5C14               case 3: CV_35F8
      case 4: CV_344E  + CV_5C1C               case 4: CV_3614  + CV_5C8C

Both tables are recovered independently from six files (two ports × PRISON,
CAVES, CAPSULE) and agree everywhere; the probe exits 1 on disagreement,
because one offset serving two cases would break the naming.

## The two things that needed real evidence

**Case 4 is the `else`, and calling it 4 is a measurement.** In the three
stages that have this dispatch the only literals ever written to `[0x0A]` are
0, 1, 3 and 4, so the default branch handles exactly 4. TANK and LAKE write
large values to the same variable and have no such dispatch — `[0x0A]` is
reused per stage, which is why no whole-game alias for it would be right.

**Direction.** The obvious test fails, and the control is what caught it: the
two switches' art are not mirror images — but neither are the *known* LEFT and
RIGHT walk arms at the same frame index. This game draws separate poses per
direction, so a mirror test cannot assign direction here at all. The test was
invalid, not the hypothesis.

The entry site assigns it, twice over and independently per switch:

| switch | evidence |
|---|---|
| `CV_35B4` | entered from blocks that have just drawn `HERO_STAND_LEFT_ARM`, `CV_331A`, `CV_332A`, `CV_3332`, `CV_333A`, `CV_3342` — the walk-left arms; callers 70:10 LEFT-named; cases 2 and 3 already carry the earned `HERO_GUN_ARM_POSE_LEFT_CASE_02` / `_CASE_03` |
| `CV_347C` | 16 entry sites, **15 of which have just drawn a `HERO_WALK_RIGHT_BODY_F*`** and none a left-facing one |

The right-hand column of that table is names this project earned by other
routes — the walk-right bodies came from four-way cross-stage consensus in the
previous pass — so the two results check each other.

## "Charge blink" is in the opcodes

The dot is drawn only when the charge `[0x06]` is at or below a threshold
`[0x30]` **and** bit 2 of a timer `[0x31]` is set. That is a low-charge blink
stated in instructions. It is corroborated by two names earned in different
stages on a sibling dot drawn under the identical guard:
`CAPSULE_HERO_AIM_HOLD_RIGHT_DRAW_LOW_CHARGE_BLINK` and
`HERO_CROUCH_ARMED_RIGHT_FRAME_CHARGE_BLINK`.

## The 13

`gun_arm_cases.map`, generated by `--proposals` rather than typed, applied with
`notes/shared-bank-naming/apply_bank_names.py --map`:

    HERO_GUN_ARM_RIGHT_CASE_01..04        and each one's _CHARGE_BLINK dot
    HERO_GUN_ARM_LEFT_CASE_01..04         and case 4's _CHARGE_BLINK dot

Both index runs are complete, 1 to 4. The left switch draws a dot only in case
4; that asymmetry is what the code does, and inventing left dots for cases 1-3
to make the two sides match would be inventing.

Verified: `make test` 29/29 and 29/29; `bank_name_offset_consistent.py --map
gun_arm_cases.map` reports all 13 defined at the offset their key encoded, and
0 actionable duplicate names. 287 offset keys remain.

## A defect in the probe, recorded

The direction detector first looked only at the switch's **head** symbol.
Case 1 is an unnamed `LABEL_<hex>` in both switches, so it found nothing and
reported the left switch's direction as undetermined — while the evidence, an
earned label reading `LEFT` in plain text, sat two lines away on case 2. It
now scans every case. A detector that reads only the first row of a table will
miss anything the table records later.


## The second switch: `[0x05]`, the waterline

A sweep of every variable tested the same way found exactly one more selecting
shared-bank art: `[0x05]`, two chains of four, in CAVES and CAPSULE on both
ports.

    $ python3 notes/gun-arm-dispatch/arm_case_table.py --var 0x05
      switch starting at CV_5DDC        switch starting at CV_5DE4
        case 0: CV_5DDC                   case 0: CV_5DE4
        case 1: CV_5CD4                   case 1: CV_5DEC
        case 2: CV_5D2C                   case 2: CV_5E44
        case 3: CV_5D84                   case 3: CV_5E9C

**This one is the control for the whole method.** All eight offsets already
had earned routine names —
`CAVES_HERO_WATER_DEPTH_SPRITE_RIGHT_CASE_01`, `..._LEFT_CASE_02` and so on —
assigning a direction and a case number by reasoning that had nothing to do
with this dispatch. The probe recovers the case numbers from the `jne`
operands and the directions from the entry sites, and agrees with all eight,
case for case and side for side. Nothing was tuned to make that happen; the
`[0x05]` run was the first thing tried after `[0x0A]`.

The names applied drop the stage prefix the routines carry
(`HERO_WATER_DEPTH_LEFT_CASE_00`, not `CAVES_...`), because the art is shared:
the same switch appears in CAPSULE, and a shared-bank name that claims a stage
would be false at half its references.

`--base` exists because the stem is the one thing the dispatch cannot supply.
The case numbers, the direction and the membership all come out of the code;
what the family *is* comes from the earned routine names sitting on it.

## The lever does not extend to the actor slot

`docs/NAMING.md` and issue #0138 bar asserting **which character** art belongs
to, not what pose it is in — the six `CV_FIGURE_CROUCH_FACING_LEFT`-style names
from an earlier pass are exactly that distinction applied. So the 148
shared-bank offsets drawn at the actor record are nameable in principle, by
pose, and the obvious question was whether a case switch selects them the way
`[0x0A]` and `[0x05]` select the hero's.

It does not. `--at actor` widens the scanner to the `[0x07]`/`[BUDDY_X]` slot —
the first version required `x=[HERO_X]` and so excluded all 148 by
construction — and swept every variable that appears in a `jne [v], n` test.
**No switch draws actor-slot art.** Whatever selects an actor's pose is not a
compare chain; it is reached some other way, most likely through the actor
record itself.

So the dispatch method is exhausted at 21 names across two variables, and the
148 stay where they were: nameable by pose, but only from a render, one at a
time.

## The other shape the same idea takes — `guarded_companions.py`

The two switches above are one form. The commoner form is a guard inline in a
frame routine:

    CAPSULE_HERO_RUN_RIGHT_DRAW_8:
        video type=0, offset=HERO_RUN_RIGHT_BODY_F08, x=[HERO_X], ...
        jne [0x0A], 0x00, DRAW_CV_265        <- a companion, only when armed

What makes this usable where the routine names are placeholders — which is
most of what is left — is that **the frame number comes from the art, not the
label**. `HERO_RUN_RIGHT_BODY_F08` was named from separate evidence, so a
routine drawing exactly one member of a named `*_BODY_F<n>` family plus a
guarded piece fixes that piece's frame without trusting any routine name.

It found two families.

**The hero's run-right gun arm — named,** see `run_right_gun_arm.map`. Five
pieces covering frames 0..9 with no gap, guarded on `[0x0A]`, the same
weapon-state variable the two switches above run on. That is the first
limb-class family in the project with complete coverage, which is why it could
be applied where every family in `../actor-sprite-sheet/` is held.

**The actor's run-right companion — found, measured, deliberately not named.**
Six pieces covering frames 0..7 with no gap, guarded `je [0x0D], 0x00` — note
the *opposite* sense from the hero's, so whatever `[0x0D]` is, these are drawn
in its zero state and calling them a gun arm would be wrong.

    CV_6108  {0}    CV_21A8 {1}    CV_21D6 {2}
    CV_2200  {3,6}  CV_2212 {4,5}  CV_224C {7}

They share a top edge at −52.0..−52.5 while their bottoms vary from −24 to
−35.5, against a body spanning −56 to 0. A fixed attachment point with a
swinging free end is what an arm looks like, and that is positional evidence
rather than the shape resemblance `../actor-sprite-sheet/` rightly refused.

Three things stop a name anyway, and all three are about the word, not the
grouping:

1. `RUN_RIGHT_LIMB` is **already taken** by a family that note holds —
   `CV_2548` {3,5,6}, `CV_2552` {2,7,8}, `CV_255C` {1,8}, a different set of
   pieces with no common top edge. Two series under one name would be worse
   than none.
2. That note reserved `ARM` for the actor pending confirmation, and
   overriding a documented decision needs better than a new argument for the
   same shape.
3. A seventh piece, `CV_2276`, belongs to the series by every sign except the
   one that matters here: it is drawn at the actor slot by unnamed labels with
   no body frame beside it, so it has no frame evidence and cannot be placed.

A live contact sheet settles that the seven are one series and nothing else.
`LABEL_1918` in CAPSULE, reachable via `setup channel=0x38`, draws all seven
in a row at y=100, x=160..280, spaced exactly 20 apart, in ascending offset
order. It disagrees with the frame ordering — `CV_6108` is frame 0 but last
in the row — so it groups the series without ordering it.
